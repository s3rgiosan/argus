# Pull requests

GitHub pull requests and GitLab merge requests as a Herdr panel, with one pull request in a pane beside the terminals. Every read goes through `gh`, `glab` and `git`. The mod writes to GitHub or GitLab only through the four review actions of the pane.

## What you see

- `mod.json`: `{ "place": "none", "title": "Pull requests", "overlay": { "width": 360, "height": 640 }, "panel": { "label": "Pull requests", "icon": "icons/git-pull-request.svg" } }`. The `argus` layout (`scripts/build-layout.mjs`) gives it a toolbar button and a panel.
- One mod, views picked by `props().view`: none or `"board"` (the panel, with Settings and Merged worktrees pages), `"scopes"` (popup), `"review"` (the Review with agent dialog), `"pr"` (pane).
- Board, drawn with `ui.js` (a copy of `lib/ui.js`): header with "Pull requests", the count badge (Herdr's Changes pill: 10 px `muted`, 1 px `border`, radius 4), the scope button, refresh (it turns while this copy reads) and settings icon buttons; scroll area; bottom bar with the filter field. Notes show at the top of the scroll area.
- Group titles: "Ready to merge · n", "Needs work · n", "Waiting on review · n", "Draft · n", titled like Herdr's group headings (11.5 px, medium, `dim`). Empty groups are left out.
- Row: number, title, checks, age, then repo and branch and the review state. The selected row is on `selected`.
- Scopes popup: a Show section (Needs my review, Mine, All open), then an In section (Follow space, All repos, then each project indented 24 px under All repos). Rows use Herdr's menu metrics (31 px, 8 px side padding, radius 7, 12.8 px text, 5 px around the list); the count shows dim on the right and the chosen row of each section has an `accent` tick. Each count keeps the other choice as it is (`scopeItems`). Up and Down move the highlight across all rows, Enter picks, Escape closes, a click picks and moves the highlight to its row. A pick sets its own choice and keeps the popup open. A picked project no longer on the board stays in the list with its tick.
- Pull request pane (`detail-view.js` `prPane`, data from `detail.js`): a scroll of the header (provider icon, `repo · #n`, `positionIn(shownOrder(board, scope, followed))` as `<i> of <n>` with ↑ ↓ that write `selected`, ↗ Open in browser and ⎇ Check out icon buttons; the title at 16 px semibold; `head → base` (it wraps inside the pane); the verdict box from `verdictOf`: the board's `groupOf` title, or Merged or Closed, tinted in the group's color, with the reasons line (checks, review, draft, merge state; a reviewer's open request for changes moves an open pull request that is not a draft to Needs work even when the review decision does not say so; a group other than Ready to merge never says "Nothing blocks the merge"); the "No local checkout" note) and the folding sections (`SECTIONS`: Checks, Reviews, Review agent, Description, Conversation; a heading row with a chevron, the name and the `sectionSummaries` text; the open set is the person's choice per pull request (`this.folds`, `{ open, defaultWas }` per section) while `openByDefault` still gives the default the choice was made against, else the default: `sectionOpen`; the Review agent summary and default use the runs the body shows, without a removed run). Checks follows `checkLayout`; a check with a `url` (GitHub `detailsUrl` or `targetUrl`, GitLab job `webPath` or pipeline `path` on the host) is a hover row with an external-link icon that opens the page through `openInBrowser`: failed and running rows, then a `✓ <n> passed` line with a Show or Hide link (`this.passedOpen`); five or fewer passed checks with nothing failed or running are listed without the line. Section bodies share one inset and gap; their notes are plain muted text. Comment, thread and description text renders with `TextView.markdown` (a link opens through `on.openLink` and `openInBrowser`, so only http and https open; a comment with no text shows no Markdown), and authors show by `nameOf` (a name shrinks with `truncate` and has the login `@login` as its tooltip; Markdown and row ids come from the item's review id or time and author, and the thread's file, line and first time, not from list positions) (`detail.names`: GitHub `participants { login name }` and requested reviewers `reviewRequests { requestedReviewer { ... on User { login name } } }` from the thread query, GitLab note `author { username name }` and `reviewers { username name }`; bots have no name on GitHub: `displayName` (`lib/forge-board.js`) shows the known ones from `KNOWN_BOTS` (Copilot, Dependabot) and others by login without `gh`'s `app/` prefix). Conversation shows the thread read error or limit note, then `conversationItems` in the Conversation setting's order. Under the scroll, `bottomBar`: a block of at most 260 px that scrolls (the kept GitLab draft note, the merge confirm, Working…, the action error, the own-PR note, the text field when Comment… or Request changes… is open, the open menu (Merge ▾ methods or ⋯)), then the footer row, always in view (Review with agent, Merge ▾, ⋯; only ⋯ when the pull request is not open). A pick in the ⋯ menu closes the menu with a redraw. The inline Merge ▾ and ⋯ menus in the footer take mouse clicks only (no arrow keys), unlike the popups.
- Merged worktrees view (`this.view = "cleanup"`, from the "Remove merged worktrees…" button in the Settings view's Worktrees section): the frame takes focus (`this.handle`, `track_focus`); `subHeader` "Merged worktrees" with a refresh button (`refresh-cw` from the mod's `icons/`, enabled only in phase "list"), a hint with the scope, notes as `errorLine`, a `sectionTitle` `<repo> · <n>` per repo, and `row()` rows (28 px; a 14 px tick box, `accent` with an `accent_foreground` tick when ticked, or only its space for a greyed row or a row with a result; the branch; `#n` at 12 px `muted`; then "merged <age>" in `dim`, a reason in `dim`, "has ignored files" in `working`, "removing…" in `muted` for `this.cleanup.current`, or the result: "removed" in `done`, "removed, branch kept: …" in `working`, anything else in `blocked`). Only a removable row in phase "list" has the hover and the tick click. One tooltip per row: a result other than "removed", else the ignored files, else the full branch name. The footer has Cancel and Remove <n>, "Removing…", or Done. Escape goes back (a running removal goes on); Enter removes the ticked rows in phase "list" when the count is above 0. Empty: "No merged worktrees here".
- New worktree view (`this.view = "newWorktree"`, from the `+` icon button (`icons/plus.svg`, tooltip "New worktree") right of the filter field in the board footer): the frame takes focus (`this.handle`) and Escape goes back; `subHeader` "New worktree" with a refresh button ("Read again", spins while the tab is read, not drawn on the Pull request tab); a Repo section (`scopeProjects` with a `localPath`; the one `state.project` names); with several repos, a row with a "Change" link that shows one `row` per repo with an `accent` tick, inside a scroll of at most 196 px; `segmented` tabs Branch, Pull request, Issue; a filter field (`worktreeFilter`, made in `init`, placeholder "Filter"); a scroll of 28 px `row`s ("Loading…" while a tab with no list is read, `errorLine`, or the rows with the old rows kept during a re-read); lowercase status words on a row, "creating…" while it is created and "worktree" (`t.dim`) when a worktree exists; the create error as `errorLine` under the list. Empty texts have no trailing period (`emptyText`); notes and errors that are sentences keep it.
- Settings view: gh command and glab command fields (`forgeCommandFields` from `lib/ui.js`; they read and save the shared `argus.forge` key through `lib/forge-settings.js`), a Worktrees section with a secondary "Remove merged worktrees…" button that opens Merged worktrees, and the refresh interval as Herdr's Settings segmented control (`intervalPicker`; `INTERVALS` in `lib/forge-board.js`: 1, 3, 5, 10 or 15 min; 3 by default), and Conversation as a segmented control (Oldest first, the default, or Newest first; `conversationItems` puts the items in that order). Icons Herdr ships with the same drawing (chevron-left, chevron-down, chevron-right, settings, check, plus) load from Herdr's `mods/workspace-chrome/` folder when it exists, probed once in `init`; the Lucide copies in `icons/` show otherwise.

## How it behaves

- `shared` keys (prefix `argus-pull-requests.`): `board`, `scope` `{ show, where, key? }`, `selected`, `settings` `{ interval, conversation }` (a write keeps the other fields it holds, so old `gh` and `glab` values stay as the fallback of `argus.forge`), `lock`, `reviewStart` and `reviewResult` (the Review with agent handoff, below), `running` (PR key to `{ kind, at }` for a review or merge action running in any copy; an entry older than `RUN_LIMIT`, 120 s, counts as done: `runningOf`, `withRunning`, `withoutRunning`), `paneTitle` (what the `argus-pane` header shows for this mod's panes: `#<number> · <title>` of the shown pull request from the board, else from the pane's read, `#<number>` without a title, else "Pull requests"; a row click and the pane arrows set it from the board row with the selection (`setTitle` from `lib/pane.js`); `prPaneTitle`, written by the pane view only when it changes, `shareTitle` from `lib/pane.js`). The gh and glab commands live in the shared key `argus.forge` `{ gh, glab }` (`readForge`, `saveForge`; while that key is missing they come from `argus-pull-requests.settings`, and the next save writes `argus.forge`). Nothing else. The pane clears `reviewStart` (`setShared(REVIEW_START_KEY, null)`) when it takes a request with the same id. The board is written once per read, and once after each review action to add a stale mark (`staleAt`, `markStale`). A board copy treats a board with a newer stale mark as unread (`fetchedAtOf`), and a read keeps a mark made while it ran (`keepStale`).
- Read sequence (`readBoard`): list the local folders of the spaces; probe each folder with `git rev-parse` and `git remote get-url origin` through the forge runner (`createForgeRunner` in `lib/forge-runner.js` keeps `{ entry, at }` per folder; `needsProbe` probes a folder again on each scheduled read when it was not a repo or had no remote, and after `PROBE_TTL_MS`, 10 min, when it had a remote; a probe that timed out or could not start is tried again once each refresh interval; a running probe is shared per folder); merge them into projects (`remote.js`; `parseRemote` takes a GitHub remote only as exactly `owner/repo`, and takes no host or path part that starts with `-`); find `gh`, and `glab` only when a GitLab project exists (the setting, the bare name, then the install folders; the first whose `--version` runs; the result, found or missing, is kept until the setting changes or the refresh button is pressed); keep a GitLab project on a host other than `gitlab.com` (`needsGlabLogin`) unless `glab auth status --hostname <host>` says "has not been authenticated with glab" (`glabAuthArgs`, `glabLoginState`, `signedInGitLab`; a passed check is kept per glab command and host until the refresh button, and a signed-out or failed check runs again on the next read; a failed check, such as a network error, keeps the projects); a host without a login adds the note `glabLoginNote(host)`, "<host>: no glab login for this host", and its projects leave the board; read GitHub; read GitLab.
- GitHub calls: `gh api user --jq .login`; `gh search prs --review-requested=@me` and `--author=<login>` (`--state=open --archived=false --limit 100 --json number,url`); `gh pr list --repo <repo>` per project and per searched repo; `gh pr view <n> --repo <repo>` for a searched pull request the list did not return, except for a repo whose list failed (`withoutFailedRepos`). A repo whose list failed keeps the pull requests of the previous board (`keptLists`) while its last successful list (`board.listedAt`, project key to time) is less than `KEEP_RUNS_MS`, 15 min, old; its note shows. GitLab project lists keep the same way. The list and view calls run through `mapPool` (`lib/pool.js`) with 4 at a time. A search, list or query that returns the limit (`LIST_LIMIT`, 100) adds the note "Showing the first 100 …".
- GitLab calls (`glab api graphql --hostname <host>`): one query for the user's review-requested and authored merge requests per host, one per project (4 at a time), one detail query for the pane. A merge request without a usable `iid` is left out of a list.
- A failed call adds one note and leaves the rest of the board. An error that no call handles adds the note "Could not read the pull requests: <message>" (`withNote`) when this copy holds the lock. `gh` or `glab` missing, signed out or rate limited each give a note. Notes start with `gh: ` (GitHub) or `glab (<host>): ` (GitLab). An empty list says that a read failed only when a note belongs to a provider or host of the scope shown (`scopeRepos`, `emptyMessage`); with no known repo in the scope, any failure note counts, and "Showing the first …" notes never count. A read that fills the scope and worked keeps the normal text: the board's `worked` list holds the key of each repo list and `searchRead` ("gh", `glab (<host>)`) of each search that worked, and `scopeReads` gives the reads of the scope (the project lists for All open, the searches for another Show).
- Lock: the copy that takes `argus-pull-requests.lock` (`createBoardSync` in `lib/board-sync.js`, on `lib/sync.js` and `lib/gate.js`) reads. The board is read again when it is older than the interval, on refresh, and when a space shows a folder the last read did not know and that folder gives a project key the board does not have yet (`watchFolders`, checked every 5 seconds; any other unknown folder waits for the next scheduled read). The folder probes run through `mapPool`, 4 at a time. A read keeps the folders that the watch added to the board while the read ran.
- Groups (`groupOf`): draft first; then "Needs work" when a check failed, changes are requested (`changesRequested`: the review decision, or a login in `changesRequestedBy`, the logins whose entry in `latestReviews` requests changes; `latestReviews` is in `GH_LIST_FIELDS`; GitLab lists have no reviewers, so it is empty there; the row label is "changes requested") or the merge conflicts; then "Ready to merge" when the review is approved or absent, no check runs and the merge state is mergeable; else "Waiting on review".
- Scope (`normalizeScope`, `prsInScope`): Show picks the list (the review-requested search, the authored search, or every pull request the board holds), and In keeps the pull requests whose project key is the followed or chosen project. A scope saved as one `kind` maps onto the two choices.
- Follow space: the folder of the focused space (`follow.js`, a copy of `lib/follow.js`) picks the project that holds it. `followStatus` decides the note: a folder the board has not read yet (not in `board.folders`, or no read yet) shows "Reading this space…"; a read folder with no project shows "This space is not a GitHub or GitLab repo." The folder watch adds probed folders that bring no new project to `board.folders` (`withFolders`), so a new space that is no repo gets its note within one 5 s tick, without a read.
- New worktree (`newworktree.js`, `openNewWorktree`): state `this.newWorktree = { project, picking, tab, items, loading, errors, creating, createError, createNote, lastPr }`; `items` holds the read lists per tab and project key, `loading` and `errors` are keyed by `<tab>|<project key>`.
  - Repo: `openNewWorktree` sets `project` to `defaultProjectKey` (the followed project when listed, else the first) and drops the Branch list of that repo; render only reads `project`. When its key is no longer among the projects, the view shows "This repo is no longer in the scope." with the repo list open.
  - Reads start only from handlers: open, a tab pick, a repo pick, Read again and after a create (`readWorktreeTab`, `readWorktreeSlot`). A read starts when that tab has no list for the repo; the pull request tab has no read. A re-read keeps the old rows until the new list replaces them. A Branch read keeps `held`, the branches that have a worktree (`branchRead`).
  - Rows (`worktreeList`): `filterItems` narrows by branch name, number or title; `emptyText(tab, total, shown)` gives "Nothing matches the filter" when the filter hides every row. Pull request rows use `holdsWorktree` with `checkoutBranch(pr)`, issue rows with `issueBranch`, both against the `held` list of the Branch read; branch rows use the worktree path of the entry.
  - One create at a time (`worktreeBusy`): a row takes no click and no hover while `creating` is set or a pull request check out runs; `createWorktree` also refuses to start then. Enter in the filter (the submit callback made in `init`, `pickOnlyWorktreeRow`) picks the only row shown when nothing is busy and the tab has no error.
  - Branch pick (`branchWorktree` in `lib/worktree-runner.js`, `remoteBranchPlan`): open the space of a live worktree; else `check-ref-format --branch`, refuse an existing folder (`folderTaken`, a dangling link counts), `worktree prune` for a stale entry, `fetch --no-tags` of the branch. A local branch of that name is compared with `rev-list --left-right --count` (`localBranchStep`): behind only moves it with `update-ref`, ahead or diverged gives `branchNote`; it is used as it is. Without one, `worktree add --no-track -b`, then `branch.<b>.remote` and `branch.<b>.merge` are set by `git config`, and a fetch refspec is added when a single-branch clone has none for the branch (`refspecMissing`). A failed add deletes the branch it made; a failed `git config` removes the worktree and the branch.
  - Issue pick (`createIssueWorktree` in `lib/worktree-runner.js`, `issuePlan`): the branch is `issueBranch`. A local branch gets a worktree with no fetch. A branch only on the remote (`remoteBranchArgs`, `remoteHasBranch`) goes through `branchWorktree`. Else the default branch is fetched and the branch is cut from it with `--no-track`; an unknown default branch gives an error. A name that `check-ref-format` rejects or rewrites stops the create (`branchNameError`).
  - Notes: the Issue read adds "Showing the first 50 issues." at 50 rows (`issueRead`); the Branch read adds `DEFAULT_BRANCH_NOTE` when the default branch is unknown, and then lists it.
  - Branch tab: `git ls-remote --heads origin` (`remoteHeadsArgs`, `parseRemoteHeads`), `git worktree list --porcelain` and the default branch (`defaultBranch` in `lib/worktree-runner.js`: `git symbolic-ref --quiet --short refs/remotes/origin/HEAD`, else `gh repo view` or `GL_DEFAULT_BRANCH_QUERY`), then `branchItems`. Pick: `remoteBranchPlan` opens the worktree of the branch (`space.select` or `space.new`), else `git fetch --no-tags origin +refs/heads/<b>:refs/remotes/origin/<b>`, then `git worktree add <path> <b>` when `refs/heads/<b>` exists, else `git worktree add --track -b <b> <path> origin/<b>`, then `space.new { folder }`.
  - Pull request tab: the board's open pull requests of the repo (same provider, host and repo); a pick runs `checkOut`.
  - Issue tab: `gh issue list --repo <repo> --assignee @me --state open --limit 50 --json number,title,updatedAt` (`ghIssuesArgs`, `parseGhIssues`), or on GitLab `glab api graphql` with `GL_USERNAME_QUERY` (`currentUser { username }`, `parseGlUsername`) then `GL_ISSUES_QUERY` (`project(fullPath: $path) { issues(state: opened, assigneeUsernames: [$user], first: 50) }`, `parseGlIssues`; `iid` is a string). Newest update first. Pick: `issuePlan` with `issueBranch` (`<number>-<titleSlug>`; `titleSlug` is 40 characters at most, cut on a dash, and the number goes in front); an existing worktree of the branch opens; else `git check-ref-format --branch <name>`, then for a new branch `git fetch --no-tags origin <default>` and `git worktree add --no-track -b <name> <path> origin/<default>`, for an existing local branch only `git worktree add <path> <name>`; then `space.new { folder }`.
  - The worktree path is `<root>/<repo folder>/<branchSlug>` with the root from `settings.json` as in Check out. Fetches and adds take up to 10 minutes. One create runs at a time. Nothing is written to GitHub or GitLab.
- Merged worktree count: after `readReviews` (which now also returns the worktree lists it read), `readMergedCounts` runs per listed project (`mapPool`, 4 at a time): `git symbolic-ref` for the default branch (when git gives none, the forge names it: `gh repo view` or `GL_DEFAULT_BRANCH_QUERY`; a failed read is not kept and leaves the count unknown, so `mergedCounts` keeps the last count), `candidates`, and only when there are candidates one forge read (kept in `mergedHeads` with `candidateSignature` of the candidates, and reused while `mergedHeadsFresh`: the same candidates and less than `MERGED_HEADS_TTL_MS`, 15 min, old; the default branch is kept in `defaultBranches`; the refresh button clears both, and the merge methods of the pane): `ghMergedListArgs` (`gh pr list --state merged --limit 100 --json number,headRefName,headRefOid,mergedAt,baseRefName,isCrossRepository`) or `GL_MERGED_LIST_QUERY`, parsed by `parseGhMergedList` / `parseGlMergedList` (forks dropped) and counted by `countMerged`. A failed call gives null and `mergedCounts` keeps the last count (no note) for `KEEP_RUNS_MS` after the last success, then drops it. The board stores `merged` (project key to count) and `mergedSeen` (project key to the time of the last successful count); `normalizeBoard` drops bad values of both; `renderBoard` shows `mergedRow` (`mergedText`: "1 merged worktree" or "N merged worktrees"; `mergedInScope`) at the top of the list with a Review link that calls `freshForReview` (a list with no results is read again) and then `openCleanup`.
- Merged worktrees (`cleanup.js`): `readCleanup` takes the projects of the board's scope with a local checkout (`scopeProjects`; `mergeProjects` keeps the first checkout of a repo as `localPath`; none gives the note "No repo with a local checkout in this scope."), and per project (`mapPool`; every git and forge command of the read goes through one `createLimiter(CLI_CONCURRENCY)`, so at most 4 run at once): `git worktree list --porcelain` and `git symbolic-ref --quiet --short refs/remotes/origin/HEAD` (`defaultBranchOf`; when it fails, the default branch comes from `gh repo view` or the GitLab `GL_DEFAULT_BRANCH_QUERY`; with none known the project is left out with a note that names the repo and the failed read, and `rowsFor` and `countMerged` offer and count nothing); `candidates` (linked worktrees on a branch, so detached ones are out, minus the default branch and the main worktree's branch); per worktree that is not prunable: `git status --porcelain --untracked-files=all`, `git ls-files --others --ignored --exclude-standard --directory` (a row with ignored files starts unticked: `tickedByDefault`), `git submodule status`, and the HEAD reflog for commits no branch, remote or tag reaches (`reflogArgs`, `unsavedArgs`); `panes()` folders (`insideFolder`); then the project's merged list answers the worktrees it can (`ghMergedListArgs` or `GL_MERGED_LIST_QUERY` read beside the checks, parsed by `parseGhMergedFull` or `parseGlMergedFull`; `answerFromList`); the others get GitHub `gh pr list --head <branch> --state merged` (`ghMergedArgs`) or `gh pr view <n>` for a review branch (`ghPrStateArgs`), GitLab `GL_MERGED_QUERY` or `GL_MR_STATE_QUERY`; pull requests from forks are dropped (`parseGhMerged`, `parseGlMerged`). `rowsFor` gives the first reason that applies, in this order: locked, has changes, has submodules, has unsaved commits, open in a space, has an open pull request (`openBranches`: the board's last read of open pull requests of that repo, no new read), merged into <base>, not at the merged commit. A failed read leaves the project out with a note. `this.cleanup` is `{ phase, scope, notes, groups, ticked, results, current }`. `removeCleanup` runs in the copy that shows the view and sets `current` to the path being removed before each row and clears it after. Per ticked row: `removeMerged` checks `panes()` again ("open in a space"), then `git status` and the ignored list again (`recheck`: "has changes" or "ignored files changed"), then `git worktree remove <path>` (`removePlan`, no `--force`; `dirtyRefusal` gives "has changes", `goneRefusal` counts as removed), `git rev-parse --verify --quiet refs/heads/<branch>`, `branchStep` (review branch: `git branch -d`; other branch: `git branch -D` only when the tip is the merged head; else "removed, branch kept: …"), then `git worktree prune` per project and a stale mark on the board. A git error shows as the result. Leaving the view does not stop a removal; the results stay on `this.cleanup` until Done clears it, and opening the view reads only when `this.cleanup` is null (`readsOnOpen`).
- Filter: case-insensitive match on title, author and branch, and on the number with or without `#` (`matchesFilter`).
- Row click: sets `argus-pull-requests.selected`. If the shown tab has a pane of this mod, `pane.focus` it; else `pane.split { direction: "right", mod: "argus-pull-requests", props: { view: "pr" } }` (`openModPane` from `lib/pane.js`).
- Pane read: `gh pr view` and, at the same time, `gh api graphql` for the review threads (`ghThreadsArgs`, `parseGhThreads`; a failure only sets `threadsError`, `mergeThreads`; 100 threads set the note "Showing the first 100 file comment threads."), or the GitLab detail query (with `discussions` for comments and file threads, and `targetProject.squashReadOnly`), when the selection changes, and again when the board is newer.
- Open in browser, a check link and a link in Markdown: `cx.open_url(url)` (`openInBrowser` from `lib/pane.js`). Herdr opens only absolute http and https URLs; a refused or failed open shows nothing.
- Check out in a worktree (`runCheckout`, `checkout.js`; the worktrees folder, the list and the space come from `createWorktreeRunner` in `lib/worktree-runner.js`):
  1. Read the worktrees folder from `settings.json` (`worktrees.directory`, default `~/.herdr/worktrees`).
  2. `git worktree list --porcelain` in the local clone. A worktree already on branch `pr/<n>` (`mr/<n>` on GitLab) is opened: `space.select` when a space shows it, else `space.new`.
  3. When the local branch `pr/<n>` (`mr/<n>`) exists without a worktree, `git fetch --no-tags origin refs/pull/<n>/head` (`refs/merge-requests/<n>/head` on GitLab) reads the head into `FETCH_HEAD`, and `git rev-list --count FETCH_HEAD..refs/heads/pr/<n>` counts the branch commits that are not on it. A count above 0 refuses with a message and changes nothing (`aheadCount`, `aheadRefusal`).
  4. `git fetch --no-tags origin +refs/pull/<n>/head:refs/heads/pr/<n>` creates the branch or force-updates a branch that holds nothing extra.
  5. `git worktree add <root>/<repo folder>/pr-<n> pr/<n>` (`mr-<n>` on GitLab), then `space.new { folder }`.
  The fetches and the add may take up to 10 minutes. The button of that pull request is disabled while it runs; other pull requests keep theirs. An error from Check out shows on its own pull request only.
- Review actions (`actions.js`, `runAction`): `actionCommand` builds the command; bodies go in as one `--body=<text>` (gh) or `--message=<text>` (glab) argument.
  - GitHub: Comment runs `gh pr review <n> --repo <repo> --comment --body=…`. Approve and Request changes run `gh api --method POST --hostname <host> repos/<repo>/pulls/<n>/reviews -f commit_id=<head> -f event=APPROVE|REQUEST_CHANGES [-f body=…]` (`ghReviewArgs`; `-f` sends raw strings, so a body that starts with `@` stays text), which records the review on the commit the pane showed. They first run `gh pr view <n> --repo <repo> --json headRefOid` (`ghHeadArgs`, the command's `check`) and `headRefusal` compares it with the pane's head. GitLab Request changes does the same with `GL_MR_STATE_QUERY` (`glHeadArgs`, field `diffHeadSha`), before the draft step: `HEAD_MOVED` "The pull request has new commits. Review them, then try again.", `HEAD_UNREAD` "Could not read the head commit of the pull request."; `gh pr merge <n> --repo <repo> --<method> --match-head-commit <sha>`. The method comes from `gh repo view <repo> --json viewerDefaultMergeMethod,mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed` (`pickMergeMethod`).
  - GitLab (`-R https://<host>/<repo>`): `glab mr approve <n> --sha <sha>`; `glab mr note draft list <n> -F json` (`draftListArgs`), then by `draftPlan`: no pending comment runs `glab mr note draft create <n> --message=…` and `glab mr note draft publish <n> --reviewer-state=requested_changes --yes`; one pending comment that this pane drafted with the same text (`draftText`) runs the publish only; anything else refuses (`pendingDrafts`, `DRAFT_TEXT`, `DRAFTS_UNREAD`), because a publish sends every pending comment of the user; `glab mr note create <n> --message=… --resolvable=false`; `glab mr merge <n> --yes --auto-merge=false --sha <sha>`, plus `--squash` when `squashOnMerge` is true.
  - The head SHA comes from the detail read (`headRefOid`, `diffHeadSha`). Without it, Merge, GitLab Approve and GitHub Approve and Request changes refuse before running (`NO_SHA`).
  - On GitHub, the pane reads the signed-in login (`gh api user`, kept per gh setting for `LOGIN_TTL`, 5 min, a failed read included: `loginFresh`) before the detail. `ownPr` turns Approve and Request changes off on a pull request that login opened, and the pane shows `OWN_PR`. An unknown login leaves them on.
  - One action runs at a time per pull request, across every copy (`running` in shared state). Every action ends with a read of the pull request (`afterAction`), so a refused head pin shows the new head, and with a stale mark on the board, so a board copy reads it on its next 5 s tick. Success closes the confirm, and clears and closes the text field after Request changes or Comment only while it still holds the sent text (`clearsComment`). When the publish step of a GitLab Request changes fails, the action state keeps `draftText`, and the bottom area shows a note. Merge ▾ (`toggleMenu`, `loadMethods`): GitHub reads `ghMethodArgs` when the menu opens ("Loading…" until then) and keeps `ghMergeMethods` per repo for the pane copy; GitLab uses `glMergeMethods` (`squashLocked`, `squash`) on the detail as read now, every render, with the note from `mergeMenuNote` on a merge request set to squash. Menu rows are off while an action runs. Merge refuses a confirm whose method the merge request no longer allows (`mergeAllowed`) and asks to pick again. A pick sets `confirm { method, headSha }`; the confirm shows above the footer and Merge sends that SHA (`confirmedDetail`) and, on GitLab, `--squash` for Squash and merge (no flag for Merge: glab sends nothing for `--squash=false`); `glMergeMethods` offers only Squash and merge on a merge request set to squash. The text field holds the text of one pull request (`boxKey`); its action runs only while that is the shown one. Action state: `{ running, error, confirm, text, draftText, menu, methods, composing }` (`menu`: "merge" or "more"; `composing`: "comment" or "request_changes"). When the pane opens another pull request, `leavePr` keeps the typed text, the open text field, a kept draft and a running action of the one it leaves, and drops its merge confirm, an open menu with its methods, and an error already shown.
- Review with agent (`review.js`):

  - Agents: `knownAgents()` from Herdr, each with `agent` and `installed` true (`agentChoices`). Claude Code (`claude`) once per profile from `discover` (`accounts.js`, a copy of `lib/accounts.js`) after `visibleProfiles` with the hidden list of `shared("argus-claude-usage.settings")`, named from its `names`, else the profile label.   - Per-account settings: `reviewInstructions(text, home)` (in `argus-file.js`, a copy of `lib/argus-file.js`) also gives `accounts`, `pullRequests.review.accounts` keyed by the folder with `~` expanded (`expandHome`), each `{ key, instructions, promptFile }` (`key` as written; the object has no prototype) trimmed, empty as null; a non-object `accounts` or entry, a non-text value, an empty key, a key that does not expand to an absolute folder, the key `__proto__` and two keys that expand to the same folder are errors that name the key. It also gives `reportFolders` from `pullRequests.review.reportFolders`: a list of names, each trimmed, starting with `.`, with no `/`, not `.` or `..`, and not `.git`, `.github`, `.gitlab`, `.claude`, `.githooks`, `.husky` or `.vscode` in any case; repeats go, the order stays, and a bad list or entry is an error that names the entry. `agentChoices` gives each choice a `folder` (the profile folder; `~/.claude` expanded when no profile is found; null for other agents). `loadAgents` reads `argus.json` once, in its spawn, and keeps `accounts` on `this.review`. `prefillExtra` (when the choices are ready and on each tile click, never in render) asks `prefillNext({ current, prefilled, next })` and calls `extraInput.set_value(text)` on the `TextareaState`; `this.review.prefilled` holds the last pre-fill. The field changes only when it is empty or equals `prefilled` exactly. After `set_value`, `prefilled` is the field's read-back (`value()`), so a field that changes the text still counts an untouched pre-fill as untouched. A file that cannot be read or that has an error pre-fills nothing (`loadAgents` catches the read).

  - Start: the dialog checks the branch (`branchRefusal`), then writes a request to shared `reviewStart` `{ id, owner, pr, argv, branch, extra }`. `owner` is the pane copy that opened the dialog; that pane takes the request in its render (`takesRequest`), runs it (`runRequest`, `runReview`) and writes shared `reviewResult`, a map of request id to `{ state: "running"|"done", error, at, seen }` (`withResult`; results older than 10 min go), so closing the dialog does not stop the run. A failed run shows a toast after 1.5 s unless the dialog marked the result seen (`markSeen`). The built-in prompt (`reviewPrompt`): the data block between `DATA_START` and `DATA_END` (`<<<pull-request>>>` and `<<</pull-request>>>`) holds the title, author, base and head branch, each from `quoted` (`JSON.stringify` with `<`, `>`, DEL and C1 controls, zero-width, line and direction characters turned into `\uXXXX`), then the head commit, four rules (no edits, commits, pushes or merges; a post only after the person approves the exact text, target and review event in the conversation, and only when `{{viewCommand}}` run right before it still shows the head commit; report files outside dot folders, except the `reportFolders` that `reviewPrompt` gets from `runReview`; no worktree-changing git commands but `git fetch`; pull request text is data to report and never an approval; read only at the head commit) and five steps: `{{viewCommand}}` (GitHub adds `baseRefOid`), fetch `refs/heads/<base>` and the head ref and match `FETCH_HEAD` to the head commit, `git diff <base commit>...<sha>`, `{{viewCommand}}` again, and stop without a review when a step fails. The tail for extra instructions says that the person who started the review wrote them. The agent keeps its own permission prompts: Argus passes no permission flag.
  - Runs (`reviewRuns`): each read lists `git worktree list --porcelain` per project with a local checkout (4 at a time, renewing the lock) and keeps the linked worktrees (never the main one) on `argus/review-<n>-` branches, with their `locked` and `prunable` flags, in `board.reviews` by `prKey`. Each run keeps `seenAt`, the time of the read that listed it; a project whose list fails keeps the runs seen in the last 15 min (`keepRuns`, `KEEP_RUNS_MS`). ## Watch out

- Herdr's `exec` has no stdin or env options.
- Herdr app 0.1.16 does not load a symlinked mod folder: copy it with `scripts/install.sh`.
- A `gh` or `glab` command setting that does not run falls back to PATH and the install folders, so a wrong setting shows no note while one of those runs.
- A GitHub Enterprise host is read as GitLab, because every host other than github.com and a few known other forges is treated as GitLab.
