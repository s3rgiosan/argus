# Pull requests

GitHub pull requests and GitLab merge requests as a Herdr panel, with one pull request in a pane beside the terminals. Every read goes through `gh`, `glab` and `git`. The mod writes to GitHub or GitLab only through the four review actions of the pane.

## What you see

- `mod.json`: `{ "place": "none", "title": "Pull requests", "overlay": { "width": 360, "height": 640 }, "panel": { "label": "Pull requests", "icon": "icons/git-pull-request.svg" } }`. The `argus` layout (`scripts/build-layout.mjs`) gives it a toolbar button and a panel.
- One mod, views picked by `props().view`: none or `"board"` (the panel, with a settings page), `"scopes"` (popup), `"pr"` (pane).
- Board, drawn with `ui.js` (a copy of `lib/ui.js`): header with "Pull requests", the count badge (Herdr's Changes pill: 10 px `muted`, 1 px `border`, radius 4), the scope button, refresh (it turns while this copy reads) and settings icon buttons; scroll area; bottom bar with the filter field. Notes show at the top of the scroll area.
- Group titles: "Ready to merge · n", "Needs work · n", "Waiting on review · n", "Draft · n", titled like Herdr's group headings (11.5 px, medium, `dim`). Empty groups are left out.
- Row: number, title, checks, age, then repo and branch and the review state. The selected row is on `selected`.
- Scopes popup: a Show section (Needs my review, Mine, All open), then an In section (Follow space, All repos, then each project indented 24 px under All repos). Rows use Herdr's menu metrics (31 px, 8 px side padding, radius 7, 12.8 px text, 5 px around the list); the count shows dim on the right and the chosen row of each section has an `accent` tick. Each count keeps the other choice as it is (`scopeItems`). Up and Down move the highlight across all rows, Enter picks, Escape closes, a click picks and moves the highlight to its row. A pick sets its own choice and keeps the popup open. A picked project no longer on the board stays in the list with its tick.
- Pull request pane (`detail-view.js` `prPane`, data from `detail.js`): header (provider icon, repo, `#n`, `positionIn(shownOrder(board, scope, followed))` as `<i> of <n>` with ↑ ↓ that write `selected`, ↗ Open in browser and ⎇ Check out icon buttons; state chip and `head → base`; the title at 18 px semibold; the "No local checkout" note), a tab strip (Conversation, Checks, Description, Agent, Details; the chosen one has a 2 px `accent` underline and stays per pane copy), the tab in a scroll area, and on an open pull request the comment bar at the bottom. Conversation: the status card (`statusRows`: checks, review, merge with `Open into <base>` or the forge's reason, agent; the agent row opens the Agent tab) with Review with agent and Merge ▾, the summary (`summaryOf`), the thread read error or limit note, then `conversationItems` (comments, reviews with their state chip and their file threads, threads with no listed review by their time) in the Conversation setting's order. Checks, Description, Agent (runs and Review with agent) and Details (author, head, base, updated, draft, merge state and reason, head commit, reviewers) show the rest.
- Settings view: gh command and glab command fields, and the refresh interval as Herdr's Settings segmented control (`INTERVALS` in `locate.js`: 1, 3, 5, 10 or 15 min; 3 by default), and Conversation as a segmented control (Oldest first, the default, or Newest first; `conversationItems` puts the items in that order). Icons Herdr ships with the same drawing (chevron-left, chevron-down, settings, check) load from Herdr's `mods/workspace-chrome/` folder when it exists, probed once in `init`; the Lucide copies in `icons/` show otherwise.

## How it behaves

- `shared` keys (prefix `argus-pull-requests.`): `board`, `scope` `{ show, where, key? }`, `selected`, `settings` `{ gh, glab, interval, conversation }`, `lock`, `reviewStart` and `reviewResult` (the Review with agent handoff, below), `running` (PR key to `{ kind, at }` for a review or merge action running in any copy; an entry older than `RUN_LIMIT`, 120 s, counts as done: `runningOf`, `withRunning`, `withoutRunning`), `paneTitle` (what the `argus-pane` header shows for this mod's panes: `#<number> · <title>` of the shown pull request from the board, else from the pane's read, `#<number>` without a title, else "Pull requests"; `prPaneTitle`, written by the pane view only when it changes). Nothing else. The board is written once per read, and once after each review action to add a stale mark (`staleAt`, `markStale`). A board copy treats a board with a newer stale mark as unread (`fetchedAtOf`), and a read keeps a mark made while it ran (`keepStale`).
- Read sequence (`readBoard`): list the local folders of the spaces; probe each folder with `git rev-parse` and `git remote get-url origin`; merge them into projects (`remote.js`); find `gh`, and `glab` only when a GitLab project exists (the setting, the bare name, then the install folders; the first whose `--version` runs; the result, found or missing, is kept until the setting changes or the refresh button is pressed); read GitHub; read GitLab.
- GitHub calls: `gh api user --jq .login`; `gh search prs --review-requested=@me` and `--author=<login>` (`--state=open --archived=false --limit 100 --json number,url`); `gh pr list --repo <repo>` per project and per searched repo; `gh pr view <n> --repo <repo>` for a searched pull request the list did not return, except for a repo whose list failed (`withoutFailedRepos`). The list and view calls run through `mapPool` (`lib/pool.js`) with 4 at a time. A search, list or query that returns the limit (`LIST_LIMIT`, 100) adds the note "Showing the first 100 …".
- GitLab calls (`glab api graphql --hostname <host>`): one query for the user's review-requested and authored merge requests per host, one per project (4 at a time), one detail query for the pane. A merge request without a usable `iid` is left out of a list.
- A failed call adds one note and leaves the rest of the board. `gh` or `glab` missing, signed out or rate limited each give a note.
- Lock: the copy that takes `argus-pull-requests.lock` (`lib/sync.js`, `lib/gate.js`) reads. The board is read again when it is older than the interval, on refresh, and when a space shows a folder the last read did not know and that folder gives a project key the board does not have yet (`watchFolders`, checked every 5 seconds; any other unknown folder waits for the next scheduled read).
- Groups (`groupOf`): draft first; then "Needs work" when a check failed, changes are requested or the merge conflicts; then "Ready to merge" when the review is approved or absent, no check runs and the merge state is mergeable; else "Waiting on review".
- Scope (`normalizeScope`, `prsInScope`): Show picks the list (the review-requested search, the authored search, or every pull request the board holds), and In keeps the pull requests whose project key is the followed or chosen project. A scope saved as one `kind` maps onto the two choices.
- Follow space: the folder of the focused space (`follow.js`, a copy of `lib/follow.js`) picks the project that holds it. No match shows "This space is not a GitHub or GitLab repo."
- Filter: case-insensitive match on title, author and branch, and on the number with or without `#` (`matchesFilter`).
- Row click: sets `argus-pull-requests.selected`. If the shown tab has a pane of this mod, `pane.focus` it; else `pane.split { direction: "right", mod: "argus-pull-requests", props: { view: "pr" } }`.
- Pane read: `gh pr view` and, at the same time, `gh api graphql` for the review threads (`ghThreadsArgs`, `parseGhThreads`; a failure only sets `threadsError`, `mergeThreads`), or the GitLab detail query (with `discussions` for comments and file threads, and `targetProject.squashReadOnly`), when the selection changes, and again when the board is newer.
- Open in browser: `open <url>` (`xdg-open` elsewhere) for an http or https URL.
- Check out in a worktree (`runCheckout`, `worktree.js`):
  1. Read the worktrees folder from `settings.json` (`worktrees.directory`, default `~/.herdr/worktrees`).
  2. `git worktree list --porcelain` in the local clone. A worktree already on branch `pr/<n>` (`mr/<n>` on GitLab) is opened: `space.select` when a space shows it, else `space.new`.
  3. When the local branch `pr/<n>` (`mr/<n>`) exists without a worktree, `git fetch --no-tags origin refs/pull/<n>/head` (`refs/merge-requests/<n>/head` on GitLab) reads the head into `FETCH_HEAD`, and `git rev-list --count FETCH_HEAD..refs/heads/pr/<n>` counts the branch commits that are not on it. A count above 0 refuses with a message and changes nothing (`aheadCount`, `aheadRefusal`).
  4. `git fetch --no-tags origin +refs/pull/<n>/head:refs/heads/pr/<n>` creates the branch or force-updates a branch that holds nothing extra.
  5. `git worktree add <root>/<repo folder>/pr-<n> pr/<n>` (`mr-<n>` on GitLab), then `space.new { folder }`.
  The fetches and the add may take up to 10 minutes. The button of that pull request is disabled while it runs; other pull requests keep theirs. An error from Open in browser or Check out shows on its own pull request only.
- Review actions (`actions.js`, `runAction`): `actionCommand` builds the command; bodies go in as one `--body=<text>` (gh) or `--message=<text>` (glab) argument.
  - GitHub: `gh pr review <n> --repo <repo>` with `--approve`, `--request-changes --body=…` or `--comment --body=…`; `gh pr merge <n> --repo <repo> --<method> --match-head-commit <sha>`. The method comes from `gh repo view <repo> --json viewerDefaultMergeMethod,mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed` (`pickMergeMethod`).
  - GitLab (`-R https://<host>/<repo>`): `glab mr approve <n> --sha <sha>`; `glab mr note draft list <n> -F json` (`draftListArgs`), then by `draftPlan`: no pending comment runs `glab mr note draft create <n> --message=…` and `glab mr note draft publish <n> --reviewer-state=requested_changes --yes`; one pending comment that this pane drafted with the same text (`draftText`) runs the publish only; anything else refuses (`pendingDrafts`, `DRAFT_TEXT`, `DRAFTS_UNREAD`), because a publish sends every pending comment of the user; `glab mr note create <n> --message=… --resolvable=false`; `glab mr merge <n> --yes --auto-merge=false --sha <sha>`, plus `--squash` when `squashOnMerge` is true.
  - The head SHA comes from the detail read (`headRefOid`, `diffHeadSha`). Without it, Merge and GitLab Approve refuse before running.
  - On GitHub, the pane reads the signed-in login (`gh api user`, kept per gh setting for `LOGIN_TTL`, 5 min, a failed read included: `loginFresh`) before the detail. `ownPr` turns Approve and Request changes off on a pull request that login opened, and the pane shows `OWN_PR`. An unknown login leaves them on.
  - One action runs at a time per pull request, across every copy (`running` in shared state). Every action ends with a read of the pull request (`afterAction`), so a refused head pin shows the new head, and with a stale mark on the board, so a board copy reads it on its next 5 s tick. Success closes the confirm, and clears the comment bar after Request changes or Comment only while it still holds the sent text (`clearsComment`). When the publish step of a GitLab Request changes fails, the action state keeps `draftText`, and the bar shows a note. Merge ▾ (`toggleMenu`, `loadMethods`): GitHub reads `ghMethodArgs` when the menu opens ("Loading…" until then) and keeps `ghMergeMethods` per repo for the pane copy; GitLab uses `glMergeMethods` (`squashLocked`, `squash`) on the detail as read now, every render, with the note from `mergeMenuNote` on a merge request set to squash. Menu rows are off while an action runs. Merge refuses a confirm whose method the merge request no longer allows (`mergeAllowed`) and asks to pick again. A pick sets `confirm { method, headSha }`; the confirm shows in the bar and Merge sends that SHA (`confirmedDetail`) and, on GitLab, `--squash` for Squash and merge (no flag for Merge: glab sends nothing for `--squash=false`); `glMergeMethods` offers only Squash and merge on a merge request set to squash. The comment bar holds the text of one pull request (`boxKey`); its actions run only while that is the shown one. Action state: `{ running, error, confirm, text, draftText, menu, methods }`. When the pane opens another pull request, `leavePr` keeps the typed text, a kept draft and a running action of the one it leaves, and drops its merge confirm, an open menu with its methods, and an error already shown.
- Review with agent (`review.js`):
  - Pane button Review with agent, on when the pull request is open and has a local checkout. It opens `openOverlay({ mod: "argus-pull-requests", props: { view: "review", pr: { key, provider, host, repo, number, title, localPath } }, kind: "dialog", modal: true, width: 460, height: 600 })`.
  - Dialog view `"review"`: title, the pull request line on `raised`, Agent tiles (128 px, radius 8, `accent` border and `selected` fill on the picked one), Model (only when the picked agent takes `--model`), Branch, Extra instructions (4 rows); the fields scroll; then the error line and Cancel (Close while a start runs) and Start, which stay in view. Escape, Cancel and Close close it at any time. Its inputs are made in `init`.
  - Agents: `knownAgents()` from Herdr, each with `agent` and `installed` true (`agentChoices`). Claude Code (`claude`) once per profile from `discover` (`accounts.js`, a copy of `lib/accounts.js`) after `visibleProfiles` with the hidden list of `shared("argus-claude-usage.settings")`, named from its `names`, else the profile label. The default profile runs the agent's `run` argv; another runs `["env", "CLAUDE_CONFIG_DIR=<folder>", ...run]`. `MODEL_AGENTS` (`claude`) get `--model <text>` (`agentArgv`).
  - Branch: `reviewBranch` (`argus/review-<n>-` + `titleSlug`, 40 characters at most, + 8 hex from `randomUUID`); `branchRefusal` checks the prefix, spaces and an empty name.
  - Start: the dialog checks the branch (`branchRefusal`), then writes a request to shared `reviewStart` `{ id, owner, pr, argv, branch, extra }`. `owner` is the pane copy that opened the dialog; that pane takes the request in its render (`takesRequest`), runs it (`runRequest`, `runReview`) and writes shared `reviewResult`, a map of request id to `{ state: "running"|"done", error, at, seen }` (`withResult`; results older than 10 min go), so closing the dialog does not stop the run. A failed run shows a toast after 1.5 s unless the dialog marked the result seen (`markSeen`). The dialog closes on success, shows the error otherwise (`resultFor`), and ends a start that will not finish (`startState`, `startMessage`): no result after 5 s says the pane is not open, a run still `running` after 120 s says it did not finish and that the worktree may be in the Agent tab; both withdraw the request from `reviewStart`, so the pane cannot run it later. `runReview`: read `settings.json` (`worktreeRoot`) and `argus.json` (`reviewInstructions`); read the pull request again (`readDetail`, which throws on a `gh` or `glab` error) and refuse a head commit that is not hex, a pull request that is no longer open, or a base branch with characters other than letters, digits, `.`, `_`, `/` and `-` (`startRefusal`, because the prompt puts the base in commands; the message names the branch); `git check-ref-format --branch <branch>` and `git worktree add -b <branch> <root>/<repo folder>/<branchSlug> HEAD` in the local checkout (`reviewPlan`); `space.new { name: "PR #<n> · <title>", folder, argv, task: reviewPrompt(...) }`; a stale mark on the board.
  - Runs (`reviewRuns`): each read lists `git worktree list --porcelain` per project with a local checkout (4 at a time, renewing the lock) and keeps the linked worktrees (never the main one) on `argus/review-<n>-` branches, with their `locked` and `prunable` flags, in `board.reviews` by `prKey`. Each run keeps `seenAt`, the time of the read that listed it; a project whose list fails keeps the runs seen in the last 15 min (`keepRuns`, `KEEP_RUNS_MS`). A row with runs shows a 6 px `accent` dot. A repo checked out as two separate clones is one project, so only the runs of the clone that `mergeProjects` keeps show.
  - Agent section: per run, the branch, Open space (`spaceFor`, else `space.new { folder }`; off for a prunable run) and Remove worktree (off for a locked run, with a note): a confirm, `git worktree remove <path>` (`removePlan`); a refusal for changes (`dirtyRefusal`) turns the confirm into "The worktree has changes. Remove it and lose them?", and its Remove adds `--force`; a worktree that is already gone (`goneRefusal`) counts as removed. A removed run hides at once and marks the board stale; it stays hidden only until the board reads again (`hidesRemoved`), so a later run at the same path shows; then `git branch -d <branch>` (`branchDelete`), and a toast when git keeps the branch. A second click while a removal runs does nothing.
- Timeouts: `gh` and `glab` 30 s; `git` reads 15 s; `git fetch` and `git worktree add` 10 min.

## Built from

- `main.js`: the `View`; `exec`, `home`, `appHome`, `readTextFile`, `checking`, `theme`, `shared`, `setShared`, `props`, `run`, `openOverlay`, `closeOverlay`, `panes`, `spaces`, `focused`, `window`, `knownAgents` from `herdr`; `randomUUID` from `crypto`; `readdir` and `readFile` from `fs/promises`; `InputState` and `TextareaState` from `gpui-base`.
- `remote.js` (repo probing and projects), `locate.js` (settings, command lookup, notes), `forge.js` (argument lists and GraphQL text), `model.js` (CLI output to the pull request model), `board.js` (board, scopes, groups, filter, row text), `worktree.js` (check out plan), `actions.js` (review and merge commands), `review.js` (Review with agent), `detail.js` (what the pane shows), `follow.js` (focused-space helpers). All pure, tested with `node --test`.
- `detail-view.js` draws the pane from plain data and handlers; it imports `gpui-kit`, `gpui-base` and `ui.js` only, and has no tests (render-checked).
- `ui.js`, `icons.js`, `menu.js`, `pool.js`, `gate.js`, `sync.js`, `follow.js` and `accounts.js` are copies of the files in `lib/`.

## Watch out

- Herdr's `exec` has no stdin or env options.
- Herdr app 0.1.16 does not load a symlinked mod folder: copy it with `scripts/install.sh`.
- A `gh` or `glab` command setting that does not run falls back to PATH and the install folders, so a wrong setting shows no note while one of those runs.
- A GitHub Enterprise host is read as GitLab, because every host other than github.com and a few known other forges is treated as GitLab.
